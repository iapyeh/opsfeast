# Maintaining the bilingual textbook

This procedure applies to `docs/textbook/en/` and `docs/textbook/zh-TW/`. The owner approved discussing and reviewing the textbook in Traditional Chinese, with English remaining the primary formal publication and external reference edition. Both editions are intended for publication together. This scope authorizes maintaining the textbook translations; it does not authorize host operations, commits or pushes by itself.

## During discussion

Use the Traditional Chinese edition for the owner's reading, discussion and content review. Apply requested editorial changes there first. The English edition may temporarily lag while discussion is in progress. Do not require immediate English rewrites for each discussion turn.

Keep corresponding chapter filenames aligned in the synchronized publication. During an explicitly requested structural discussion, the Chinese edition can lead with renamed, split or reordered chapters; record the full mapping below and align the English paths/navigation before a commit. Keep command arguments, configuration keys, API names, data-field names and result identifiers consistent with implemented interfaces. Translate prose naturally rather than mechanically. Preserve targets, privileges, side effects, persistence, failure/partial/unknown states, source-time meaning, recovery and verification limits. Keep exact product contracts in the canonical references; translations cannot override implemented behavior.

When a chapter acquires a substantive difference, update the synchronization status below with the affected filenames and intended changes. Use `pending English synchronization` while Chinese revisions lead, or identify the reverse direction if a product correction first changes English. Editorial approval must come from the human; a generated translation or automated check is not approval.

## Audience and authorial voice

The textbook is written by the OpsFeast development team for human readers: system administrators, related product managers and deputies. Explain the product, share the team's experience and teach practical workflows in that voice. Use "we" for the team's design choices and actual experience, and address the reader directly. Example prompts teach a human how to work with their own agent; the textbook itself is not an instruction sheet addressed to a development agent.

Lead with purpose, benefits, the next useful action and how to understand its result. Overview should help readers understand why the product exists and how to get started. Put setup details in installation, operational boundaries beside the relevant action, and precise contracts in canonical references. Describe real limits with useful next steps rather than repeating generic disclaimers or lists of unimplemented unrelated features.

Write chapter and section headings as affirmative statements centered on the reader's useful outcome. Prefer concrete benefits such as rapid inventory, immediate reuse, team collaboration, a workflow adapted to the reader's own environment, or retaining decisions while the agent handles execution. Avoid rhetorical-question headings and generic product/activity descriptions when the section can name the benefit directly. Keep concept/reference labels precise where they aid navigation; do not turn every technical label into a slogan or promise unsupported capabilities. When changing headings, update navigation and incoming fragments. Apply this principle to future textbook revisions and the English synchronization; this review updates overview and its navigation rather than bulk-renaming the rest of the book.

For a procedural chapter such as installation, use numbered imperative headings that name the reader's concrete action. Introduce the end-to-end goal before explaining new-installation versus existing-environment branches. Give each step an action and a completion criterion; mark alternatives as choose-one and optional commands as optional. Separate commands the agent performs from commands the reader should run, so readers do not repeat completed work. A final numbered handoff/acceptance step can serve as the chapter's next step. Benefit-oriented affirmative headings remain appropriate for conceptual chapters such as overview; do not apply that preference in place of actionable procedural instructions.

Make human/agent responsibility explicit in procedural chapters. Opening an agent/workspace and submitting a prompt are reader actions; receiving that prompt starts the agent's task. Do not describe every step as agent-executed. Each step should distinguish the reader's action, what the agent can assist with, and observable completion. Use the Chinese labels “你要做的事”, “agent 會做的事” and “完成判準” consistently. Prefer “使用 agent 時” for choosing agent-assisted operation; “沿用” should describe actual reuse of existing settings/results or continuation of the same conversation, not merely using an agent. Do not invent agent work for a human-only step just to fill the role label. Label alternative operating routes A/B/C rather than sequential substeps and explain when each is suitable.

Keep numbered steps within the chapter's actual work. A link sending the reader to another chapter is a short next-chapter navigation item, not an additional numbered action that repeats that chapter's contents. Keep chapter-local comparison labels as plain text when the chapter is short and links provide no benefit; do not add fragile fragment navigation merely because a table has option names.

Whenever a reader action delegates a concrete task to their agent, provide an adjacent copyable prompt, preferably in a `text` code fence with a copy button. Include the task, context/target selection, expected result and actual read/write scope. Reuse a complete prompt already provided for that same action instead of duplicating it. Use known conversation context; if a required target is absent, have the prompt ask for it rather than guessing. Do not make readers compose routine agent instructions themselves. Distinguish whole-workflow prompts from per-step prompts so readers do not repeat already-completed work or approval.

Keep editorial provenance, this chat's execution history, parser/QA records, translation parity and commit/push status in this maintenance document or the task handoff. Do not insert third-person narration such as "the project maintainer reported" into the team's own experience, or public prose about what this documentation task did not independently verify. Do not turn the book into an audit report or a running record of its creation.

Accuracy still matters. Preserve actual command effects, versions, data loss/recovery behavior, partial/unknown outcomes and reader-relevant platform or dependency gaps. Use specific scope and natural contextual wording; never fabricate team actions or convert one case into a universal performance/Token benchmark. Keep external security facts linked to primary sources. These editorial principles apply to the whole textbook and must be carried into English synchronization.

The owner can leave editorial feedback between standalone lines `comment start:` and `comment end.` in a textbook source file and ask the agent to read that file. Treat the enclosed text as the owner's review note for the referenced passage, not publication prose. Read its surrounding context, implement clear requested edits, and ask only about consequential ambiguity. When a note is fully implemented, remove that note and its delimiters, then report the change; leave unresolved notes available for discussion. Do not remove unrelated prose or other notes. These editorial comments do not independently authorize commits, pushes or operational actions.

## When the owner requests a commit

Before committing, review all pending textbook work and the recorded synchronization status. Revise the English edition to incorporate the finalized Chinese changes, then compare both editions for semantic and operational consistency. A commit request authorizes this necessary English synchronization without asking for the same approval again.

Validate chapter/file correspondence, relative links and local heading fragments, executable examples, timestamps and the complete intended diff. Use the repository's documentation-level checks for prose-only work; apply the appropriate higher validation level if product code/contracts or executable maintenance tools also change. Update modified documents' existing footers in Asia/Taipei time and avoid timestamp-only edits to otherwise unchanged files.

Resolve material ambiguity before claiming synchronization. Do not mark unresolved technical differences as synchronized. Once applicable documentation, skill-routing and validation work is complete, mark the corresponding content synchronized and commit both editions in one explicitly reviewed allowlist. Preserve unrelated/private files. This procedure follows the repository's existing contribution gate and does not create another routine approval step.

## When the owner requests a push

Review the complete set of changes/commits to be pushed and confirm that the English and Chinese editions intended for delivery are synchronized and included. If a push request requires finishing and committing pending textbook work, complete that work within the requested publication scope and the contribution rules. Push both editions together to the authorized destination. A commit-only request never authorizes a push; neither request authorizes a release, tag, deployment or unrelated changes.
