# System inventory collection groups

Recipe 0.4.0 keeps one inventory collection program with independently selectable jobs. This table is the shared human/AI-agent reference for collection content, default elapsed intervals and support limits. For exact commands, configuration, YANG mapping, provenance, retention and cron behavior, read [Inventory jobs](../../../../docs/inventory-jobs.md).

The `inventory` command implements these groups. `inventory describe --json` exposes the versioned [property catalog](collection.json), including stable readable property IDs, standard/extension YANG node paths and entity keys. Existing whole-snapshot results and the new job observations are separate contracts; no migration or conversion of old history is performed.

## Collection groups and default intervals

“Existing” identifies the original 25 fields/collections reused by the selective collector. It does not promise every value on every platform. “Added” identifies probes/data definitions introduced by the job flow. Default intervals are operational starting points, not guarantees that changes cannot occur faster. A day is 24 elapsed hours; a week is 7 days. Administrators can override intervals or disable jobs per instance/host without editing the recipe.

| Job ID | Human-readable title | Collection content | Default interval | Coverage and interpretation |
| --- | --- | --- | --- | --- |
| `hardware-baseline` | Hardware baseline | CPU model/count, total memory, vendor/model/serial/UUID, architecture and virtualization type. | 7 days | Existing: `hardware.cpu_model`, `hardware.logical_cpus`, `hardware.memory_total_bytes`, `hardware.vendor`, `hardware.model`, `hardware.serial`, `hardware.uuid`, `system.architecture`, `system.virtualization`. Visible host/VM scope is not guaranteed physical inventory or workload allocation. |
| `system-configuration` | System configuration | Hostname, platform, distribution/userland name/version, kernel name/release/build and timezone abbreviation. | 1 day | Existing: `system.hostname`, `system.platform`, `system.system_name`, `system.system_version`, `system.kernel_name`, `system.kernel_release`, `system.timezone`. Added: `system.kernel_version`. Keep distribution and utsname meanings separate. |
| `network-configuration` | Network configuration | Interface inventory, names/MAC/MTU, IP addresses/prefixes and resolver-file information. | 1 day | Existing: configuration columns of `network.interfaces` and `network.dns_servers`. Added: explicit IPv4/IPv6 standard-node projections. Link MTU and resolver-file contents are not assumed to be IP MTU or complete DNS policy. |
| `software-inventory` | Installed software | Installed package names/versions or the platform's supported installed-item representation. | 1 day | Existing: `software.packages`. macOS currently lists Installer receipts; ESXi preserves VIB entry lines. This is not universal application coverage. |
| `storage-layout` | Storage layout | Filesystem sources/mountpoints and block-device names/types/sizes/filesystem types/models where available. | 1 day | Existing: `storage.block_devices` and layout columns of `storage.filesystems`. These are observed mounts, not configured mount policy. Filesystem total capacity belongs to the capacity job. |
| `storage-capacity` | Storage capacity | Filesystem total/used/available bytes and usage percentage; inode totals/usage; swap total/used/available bytes. | 15 minutes | Existing: capacity columns of `storage.filesystems`, from bounded `df -Pk`. Added: Linux inode/swap probes. Available space is not assumed to equal total minus used. |
| `service-state` | Services and listening endpoints | Platform-visible services and current TCP/UDP listening/bound endpoints. | 5 minutes | Existing: `services.services`, `network.listening_endpoints`. Enabled scripts, launchd entries and systemd states have different meanings; they do not establish universal service health or process inventories. |
| `network-state` | Network operational state | Interface operational state and observed routing tables. | 5 minutes | Existing: state columns of `network.interfaces` and `network.routes`. Source rows/coverage vary by platform; route rows are not silently equated with full standard RIB entries. |
| `system-runtime` | System runtime | Uptime and boot-time context for restart/counter interpretation. | 5 minutes | Existing: `system.uptime_seconds`. Added: labeled controller-time-minus-uptime boot estimate; it is not an authoritative target boot timestamp. |
| `resource-metrics` | Resource utilization | CPU utilization, 1/5/15-minute load averages, memory total/available/pressure, disk counters and interface traffic/error/discard counters. | 1 minute | Added Linux probes. CPU utilization uses two samples and a recorded window; load average is a different measurement. Raw cumulative counters are not rates. Missing PSI/tools remain gaps. |
| `hardware-sensors` | Hardware sensors | Available thermal-zone temperatures and hwmon fan speeds, with source sensor paths and units. | 1 minute, disabled by default | Added Linux probes; enable explicitly after reviewing support/cost. No assumed installation, firmware access or standard component-identity mapping. |

All 25 original fields/collections appear above. A job may execute multiple commands; a shared measured result can supply selected properties with the same original source time. Utility selection returns only requested properties. Newly measured equal values remain new historical samples, rather than being discarded as unchanged.

For DHCP/VPN/ephemeral interfaces, consider a 5-minute network configuration interval. For fast-growing log/database filesystems, consider 1–5-minute capacity samples. After hardware/VM resizing, OS/network changes, deployments or storage expansion, use an explicit immediate refresh of the relevant group. Such a refresh does not postpone the normal schedule. These are recommendations, not automatic event triggers or evidence that short-lived changes will be observed.

Accounts, sudo/SSH/firewall policy, certificate expiry, SMART/RAID/power health and managed VM/container inventories require separate reviewed probes and scope. They are not implied by this table. Read-only hardware queries can still have device-specific costs.

## Rules for administrators and user AI agents

- Discover property/job IDs with `inventory describe`; use existing reviewed probes before writing new automation. The recipe owns parsing and model correspondence; retention owns validation/storage, while consumers such as Vault present retained data.
- Query immediately without records using `inventory query --host HOST --property PROPERTY`. Add `--save` and optional `--note` to preserve a comparison sample, or use `inventory run --job JOB` for an immediate saved group. Use `--json` for agent parsing. These are real target operations, independent of schedule configuration authorization.
- Scheduling is explicitly enabled per host in `inventory.yaml`. Recipe defaults are overridden by shared job settings, then host job settings. Titles are display text; stable IDs are selectors. No enabled host means no collection. A minute cron entry invokes a deterministic dispatcher, not an AI session.
- Due selection occurs before connection/privilege work. Attempts, including failures, advance to the next ordinary interval. There is no automatic retry, backoff or notification. Preserve errors and missing values for later analysis. Not due/disabled is not a successful empty sample.
- Each measured group/property keeps its sample time, source probe, actor scope, model definition and entity keys. Null, zero, false and empty successful collections remain distinct. A manual note is context, not proof that a cleanup action was executed.
- Query retained structured data for trends; never infer freshness from a rebuilt Markdown page. Latest views can mix sample ages and must show original source times. A partial property refresh does not clear unrelated properties. A new failed attempt leaves a gap instead of filling it with older success.
- Enumeration completeness matters: only complete successful collection of a declared scope can support disappearance claims. Array position is not entity identity, and host/device replacement or namespace changes require identity review. Preserve source-scoped identity warnings.
- Retain all actual samples and their provenance, even when storage grows. No automatic compaction, downsampling, deletion or unlimited-storage guarantee is introduced. Rates require comparable counter samples, valid elapsed time and reset/wrap/restart handling; do not interpolate gaps silently.

## Standards and verification

Use existing public IETF/OpenConfig YANG modules before extensions, fixing module revisions and source hashes. See [the canonical guide](../../../../docs/inventory-jobs.md#yang-mapping-and-data-interpretation), [RFC snapshots](yang/SOURCE.json), [OpenConfig snapshots](yang/openconfig/SOURCE.json), the [catalog](collection.json) and [extension module](opsfeast-inventory.yang). Samples reference schema nodes; they are not complete RFC 7951 datastore documents and do not claim full module or NETCONF/gNMI conformance. Missing properties do not need to be filled to complete a standard module.

Linux has the broadest source coverage; the added inode/swap, utilization/pressure/counter and sensor probes are Linux-specific. Other platforms preserve explicit unsupported gaps. Current [source/platform limits](../../../../docs/inventory-access.md#inventory-values-010-field-catalog) remain relevant to reused probes. Public synthetic tests and offline model/schema checks are separate from native host/SSH/privilege evidence. Read the [delivery verification report](../../../../docs/inventory-jobs.md#delivery-verification-2026-10-20) before claiming a platform or command was validated on a real target.
